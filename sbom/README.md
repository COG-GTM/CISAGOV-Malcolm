# Malcolm software bill of materials (SBOM)

This directory holds a machine-readable inventory of everything Malcolm ships, one
set per deployable, in two formats and two views, with vulnerability and license
data attached. It is regenerated by `sbom/generate.sh` (locally) and by the
`sbom-on-release` GitHub Actions workflow (on every `v*` release tag).

Current contents are summarized in [`summary.md`](summary.md); when and from what
they were produced is in [`provenance.json`](provenance.json).

## Deployables

| Deployable | Source view scans | Built view scans |
|---|---|---|
| one entry per `Dockerfiles/<name>.Dockerfile` (24) | the repository files that Dockerfile `ADD`s/`COPY`s into the image, plus the Dockerfile itself | the published image `ghcr.io/idaholab/malcolm/<name>:<version>` (`linux/amd64`), read straight from GHCR; nothing is built locally and Docker Hub is not contacted |
| `installer` | `scripts/` (`install.py`, `configure`, `control.py`, `scripts/installer/`, shared `malcolm_*.py`) | a fresh `pip` environment resolved from `scripts/installer/requirements.txt`; the exact pins are in `built/installer.requirements-resolved.txt` |

Image names differ from Dockerfile names in three cases: `filebeat` → `filebeat-oss`,
`logstash` → `logstash-oss`, `nginx` → `nginx-proxy`.

Why two views: the source view answers "what does this repository declare it depends on";
the built view answers "what is actually inside the image people run", including the base
image's operating-system packages, binaries downloaded at build time, and transitive
dependencies. A CVE answer should always be read from the built view; the source view
tells you whether the fix is a change in this repository or in an upstream image.

## Layout

```
sbom/
  README.md                 this file
  summary.md                counts per deployable (generated)
  provenance.json           commit, image digests, tool versions, timestamp (generated)
  vulns.csv                 one row per (view, deployable, package, OSV record) (generated)
  licenses.csv              one row per (view, deployable, component) with copyleft flag (generated)
  SHA256SUMS                SHA-256 of every file in this directory (generated)
  source/<deployable>.cdx.json    CycloneDX 1.5 JSON, source view
  source/<deployable>.spdx.json   SPDX 2.3 JSON, source view
  built/<deployable>.cdx.json     CycloneDX 1.5 JSON, built view
  built/<deployable>.spdx.json    SPDX 2.3 JSON, built view
  built/installer.requirements-resolved.txt
  osv/source/<deployable>.osv.json   osv-scanner results for the source SBOM
  osv/built/<deployable>.osv.json    osv-scanner results for the built SBOM
  generate.sh               regenerates everything above
  tools/cve_lookup.sh       the one-command CVE check described below
  tools/dockerfile_sources.py, tools/enrich.py, tools/normalize.py,
  tools/spdx-license-ids.json, tools/manifest.sh   helpers used by generate.sh
```

## "Are we exposed to CVE-XXXX-NNNN?" in one command

```bash
sbom/tools/cve_lookup.sh CVE-XXXX-NNNN
```

It searches every `osv/*/*.osv.json` for the identifier, both as the OSV record id and
as an alias (most CVEs appear as aliases of a distro record such as `DEBIAN-CVE-…`,
`ALPINE-CVE-…`, or a `GHSA-…`/`PYSEC-…` record). It prints one line per
(view, deployable, package, version) that is affected, with the fix version OSV lists,
and exits 0 when the identifier is present anywhere and 1 when it is not.

The same query without the helper, if you only have `jq`:

```bash
jq -r --arg id CVE-XXXX-NNNN '.results[]?.packages[]? as $p | $p.vulnerabilities[]?
  | select(.id == $id or ((.aliases // []) | index($id)))
  | [input_filename, $p.package.name, $p.package.version, .id] | @tsv' sbom/osv/*/*.osv.json
```

### Worked example

`CVE-2026-102598` is a Werkzeug `safe_join()` flaw (Windows special device names;
CVSS 4.0 score 6.3, medium) present in the results at the time of writing:

```console
$ sbom/tools/cve_lookup.sh CVE-2026-102598
view   deployable  ecosystem  package   version  osv_id               fix
built  api         PyPI       werkzeug  3.1.8    GHSA-g6x2-hccm-hh4m  fixed in 3.1.9
built  api         PyPI       werkzeug  3.1.8    PYSEC-2026-4312      fixed in 3.1.9
$ echo $?
0
```

Reading it: yes, exposed. The published `api` image (`ghcr.io/idaholab/malcolm/api:26.09.0`)
contains `werkzeug 3.1.8`; two OSV records (the GitHub advisory and the PyPI advisory)
carry this CVE as an alias, and both say 3.1.9 fixes it. The same package is absent from
the `source` view because `api/requirements.txt` pins Flask, not Werkzeug (it is a
transitive dependency), so the fix is to rebuild the image with the updated transitive
pin. The CSV row for the same finding, including the CVSS vector, is in `vulns.csv`:

```console
$ grep CVE-2026-102598 sbom/vulns.csv
built,api,PyPI,werkzeug,3.1.8,GHSA-g6x2-hccm-hh4m,CVE-2026-102598,6.3,medium,CVSS:4.0/...,3.1.9,Werkzeug safe_join() allows Windows special device names
```

An identifier that is not present exits 1:

```console
$ sbom/tools/cve_lookup.sh CVE-1999-0001
CVE-1999-0001: not present in any Malcolm deployable (checked 50 OSV result files)
$ echo $?
1
```

### Reading the answer

- A hit under `built` means the package version is inside the published image for the
  Malcolm version in `provenance.json`. That is the exposure answer. Whether the vulnerable
  code is reachable is a separate question the SBOM cannot answer.
- A hit under `source` only (none under `built`) means the repository declares the
  dependency but the image carries a different version; check `built/<deployable>.cdx.json`
  for what actually shipped.
- A hit for an operating-system package (ecosystem `Debian`, `Alpine`, …) is fixed by a
  newer base image, not by a change in this repository. Check the `FROM` line listed under
  `base_images` in `provenance.json`.
- "Not present" means none of the inventoried components match an OSV record for that id.
  It is not proof of absence; see the limits below.

## Limits a reviewer should know

- OSV coverage. Vulnerability data comes from https://osv.dev at generation time. OSV has
  strong coverage for Debian, Alpine, PyPI, npm, Go, Maven, RubyGems and crates.io. Red Hat
  UBI packages (`keycloak`, `dashboards`, and the Logstash `manuf-builder` stage) and
  vendor binaries that syft records without a purl are not matched. Cross-check those
  images with Trivy or Grype if they matter to you.
- Platform. Only `linux/amd64` images are scanned. Malcolm also publishes `linux/arm64`
  images; their OS package versions can differ.
- Point in time. The CycloneDX/SPDX inventories describe the image digests in
  `provenance.json`. The OSV results are only as current as `generated_at` there; re-run
  `generate.sh` (or the workflow) to refresh them against the same images.
- Unpinned Python requirements. Several `requirements.txt` files in this repository use
  `>=` bounds. In the source view syft records the lower bound as the version
  (`SYFT_PYTHON_GUESS_UNPINNED_REQUIREMENTS=true`), so compare against the built view
  before acting on a source-view hit.
- Installer dependencies. `scripts/installer/requirements.txt` declares `requests`,
  `psutil`, `colorama` and `distro`, but the scripts under `scripts/` also import
  `ruamel.yaml`, `python-dotenv`, `customtkinter`, `python-slugify`, `python-rapidjson`,
  `netaddr`, `libarchive` and `zeekscript` (installed by the ISO build and documented in
  `docs/host-config-linux.md`, not by that requirements file). The installer SBOMs therefore
  cover only what the requirements file declares. Treat this as a configuration-management
  gap, not as proof those packages are absent.
- License identifiers. `tools/normalize.py` runs after syft on every file. License ids
  that are not in the SPDX list embedded in the CycloneDX 1.5 schema
  (`tools/spdx-license-ids.json`), either because syft copied them verbatim from a
  Debian/Ubuntu copyright file (`UnRAR`, `SMAIL-GPL`, `Artistic-dist`, `python-ldap`) or
  because they postdate that schema (`Unicode-3.0`, `AMD-newlib`, `HPND-*`, `OAR`), are
  moved to `license.name` in CycloneDX and to `LicenseRef-<id>` entries in
  `hasExtractedLicensingInfos` in SPDX. The original text is kept in both cases; the
  generator prints which ids it touched.
- SPDX validator note. syft writes `filesAnalyzed: false` on every package while still
  recording `CONTAINS` relationships to the files each OS package owns. `pyspdxtools`
  flags that combination as invalid; the documents parse and are otherwise conformant.
  CycloneDX files validate cleanly with `cyclonedx validate --input-version v1_5`.
- Go standard library. syft records the Go runtime as `stdlib` version `go1.23.3`.
  osv-scanner cannot parse that spelling and would report every historical stdlib advisory
  as affecting the image, so `generate.sh` feeds osv-scanner a scan-only copy with the
  version written `1.23.3`. The committed SBOMs keep syft's spelling, which is why the
  `version` column for `stdlib` differs between `vulns.csv`/`osv/` (`1.23.3`) and the
  CycloneDX/SPDX files (`go1.23.3`).
- pip and setuptools appear in `built/installer.*` because they are part of any Python
  virtual environment; they are tooling, not installer dependencies.
- File names are stable (`<view>/<deployable>.cdx.json`) rather than dated so that the
  lookup command and the CI diff keep working; the date and commit live in `provenance.json`.

## Regenerating

Prerequisites: `syft`, `osv-scanner`, `python3` (3.10+), `git`, `jq`, network access to
`ghcr.io` and `api.osv.dev`. Pinned versions used by CI are in
`.github/workflows/sbom-on-release.yml`.

```bash
sbom/generate.sh                      # Malcolm version from docker-compose.yml
MALCOLM_VERSION=26.10.0 sbom/generate.sh
ONLY="api zeek" sbom/generate.sh      # regenerate a subset while iterating
SKIP_BUILT=1 sbom/generate.sh         # source views only (no registry access)
```

Every regeneration changes every file (CycloneDX `serialNumber`, SPDX `documentNamespace`
and timestamps are fresh each run). To check that an inventory is unchanged, compare the
set of `purl`s:

```bash
jq -r '.components[].purl' sbom/built/api.cdx.json | sort > /tmp/a
# ... regenerate ...
jq -r '.components[].purl' sbom/built/api.cdx.json | sort | diff /tmp/a -
```

Verify integrity:

```bash
(cd sbom && sha256sum -c --quiet SHA256SUMS)
```

## CI: `sbom-on-release`

`.github/workflows/sbom-on-release.yml` runs on every pushed `v*` tag (and on manual
dispatch with an optional image tag). It installs pinned, checksum-verified `syft` and
`osv-scanner`, runs `sbom/generate.sh`, verifies `SHA256SUMS`, uploads the directory as a
workflow artifact, attaches a tarball plus `SHA256SUMS`, `summary.md` and
`provenance.json` to the GitHub release when one exists for the tag, and opens a pull
request against `main` that refreshes the committed copy. Because the job scans the
published images, it expects `ghcr.io/idaholab/malcolm/*:<version>` to exist for the
version named in `docker-compose.yml` at the tagged commit; if the images are pushed after
the tag, re-run the workflow with `workflow_dispatch`. Opening the pull request requires
"Allow GitHub Actions to create and approve pull requests" to be enabled in the
repository's Actions settings.
